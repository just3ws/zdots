## Benchmark (2026-06-29) — M4 16GB (base, ~60 GB/s memory bandwidth)

**llama.cpp (Qwen3-8B Q4_K_M, current):** 18.6 tok/s generation
**MLX steady-state (Qwen2.5-Coder-7B-4bit, proxy):** 19.2 tok/s — GPU confirmed (Device(gpu, 0))

Both at the **hardware ceiling**. A 4-bit ~8B model requires ~3.5 GB of weights loaded per forward pass; at M4 base bandwidth (~60 GB/s) that yields ~17-20 tok/s. No software path can exceed this — both llama.cpp Metal and MLX are already memory-bandwidth bound.

**Verdict: no migration.** llama.cpp stays. The gap (~3%) is measurement noise.

Qwen3-8B MLX not used directly (download would be ~4-5 GB); Qwen2.5-Coder-7B-4bit used as a proxy (same size class, same quantization level, same result). The conclusion is chip-level, not model-specific.

To improve: the upgrade path is the chip (M4 Pro/Max with 2-4× bandwidth) or speculative decoding with a 1-2B draft model. Both are out of scope here.
<!-- SECTION:NOTES:END -->

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
No migration. llama.cpp and MLX both land at ~19 tok/s on M4 16GB — hardware-bandwidth limited, not software. Switching would gain nothing. The only path to faster inference is M4 Pro/Max (2-4× bandwidth) or speculative decoding.
